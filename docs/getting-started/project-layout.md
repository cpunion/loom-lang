# Project layout

New Loom projects should use a manifest. The directory containing `loom.toml`
is the root of a named, versioned module. Source starts directly in that
directory; `src/` has no special meaning.

Loom does not currently provide a project generator. Create the files directly:

```text
hello/
├── loom.toml
├── loom.lock              # generated by `loom resolve`
├── main.loom              # package hello
├── main_test.loom         # tests for package hello
├── greeting/
│   └── message.loom       # package hello.greeting
└── target/                # generated artifacts and caches
```

## Minimal manifest

```toml
schema = 2
language = "0.3"

[module]
name = "hello"
version = "0.1.0"

[[target]]
name = "hello"
kind = "bin"
entry = "hello.main"
```

`schema` selects the manifest format. `language` selects the source-language
semantics and should be written explicitly. The current compiler accepts
language version `0.3`.

The module name and version identify a node in the resolved dependency graph.
Versions use Semantic Versioning. There is no `sources` field: the manifest
directory is always the module root.

## Directory packages

Create `main.loom` in the module root:

```loom
import hello.greeting.message

pub fn main() {
    assert message() == "hello"
}
```

Create `greeting/message.loom`:

```loom
pub fn message() Text {
    "hello"
}
```

Every directory containing `.loom` files is one package. The module-root
directory has the module name, `hello`; its `greeting/` subdirectory is package
`hello.greeting`. All directory segments must match `[a-z][a-z0-9_]*`.

File names do not contribute to package paths. Files in one directory share a
declaration namespace and can use each other's private declarations. Crossing a
directory package boundary requires `pub` and an explicit single-symbol
import. Loom has no wildcard, grouped, or alias imports.

Source files have no `module` header. The word `module` is an ordinary
identifier. A nested `loom.toml` starts a different module, so discovery for an
outer manifest does not descend into that nested module.

## Tests

Tests live beside the code they exercise and use the suffix `_test.loom`.
Create `main_test.loom`:

```loom
test fn messageIsHello() {
    assert message() == "hello"
}
```

`test fn` and `test async fn` declarations are valid only in `*_test.loom`
files. `loom test .` runs the current directory package; `loom test ./...`
runs every package below the manifest root. Neither form includes or runs
tests shipped with dependencies.

Production commands—`check`, `build`, `run`, and library creation—exclude
`*_test.loom`, so test-only declarations cannot enter a production artifact.
There is no test target and `loom test` does not accept `--target`.

## Build targets

The manifest supports two target kinds:

| Kind | Purpose | Entry |
| --- | --- | --- |
| `bin` | Executable selected by `build` or `run` | Required for a non-default exported entry |
| `lib` | Portable, validated `.loomlib` module | Not used |

Select a named binary or library target with `--target`:

```sh
loom check --target hello .
loom build --target hello --output target/hello .
loom test .
```

An executable entry must take no parameters and return `Unit`. Its `entry`
value is a fully qualified package function such as `hello.main` or
`hello.server.start`.

A `.loomlib` is a versioned source-and-interface artifact for Loom module
dependencies. The consuming compiler checks and lowers its embedded sources
with the rest of the project; it is not a stable native ABI, shared library,
or FFI format.

## Dependencies and lockfiles

Path dependencies are a useful starting point:

```toml
[dependencies]
utility = { path = "../utility", version = "^1" }
```

The table key is the dependency alias and therefore its local import prefix. A
package in that module might be imported as `utility.math` regardless of the
dependency checkout's directory name.

Resolve the graph and write `loom.lock`:

```sh
loom resolve .
loom --locked check .
```

Commit `loom.lock` for executable projects and use `--locked` in automation so
an unexpected graph change fails instead of silently rewriting the lockfile.
See [Packages and dependencies](../guide/packages-and-dependencies.md) for path,
registry, artifact, feature, and offline behavior.

## Generated state

The default persistent cache lives below `target/loom/cache/v8`. Build outputs
also default below `target/loom`. These paths are implementation details and
should not be committed.

Inspect or prune the cache explicitly:

```sh
loom cache stat .
loom cache prune .
```

Use `--no-cache` for a cold compiler run or `--cache-dir DIR` to select another
cache root. Cache entries and generated artifacts are validated and versioned,
but they are not source-level compatibility guarantees.
