# Project layout

New Loom projects should use a manifest. The compiler also accepts standalone
source files and directories, but a `loom.toml` project gives targets, package
identity, dependency resolution, and a lockfile.

Loom does not currently provide a project generator. Create the files directly:

```text
hello/
├── loom.toml
├── loom.lock              # generated by `loomc resolve`
├── src/
│   └── main.loom
└── target/                # generated artifacts and caches
```

## Minimal manifest

```toml
schema = 1
language = "0.3"

[package]
name = "hello"
version = "0.1.0"

[[target]]
name = "hello"
kind = "bin"
entry = "hello.main"

[[target]]
name = "unit"
kind = "test"
```

`schema` selects the manifest format. `language` selects the source-language
semantics and should be written explicitly. The current compiler accepts
language version `0.3`.

Package names and versions identify nodes in the resolved graph. Versions use
Semantic Versioning. The default source root is `src`; declare a different list
with `sources = ["src", "generated"]` under `[package]` only when necessary.

## Source modules

Create `src/main.loom`:

```loom
module hello

pub fn main() {
    let answer = 40 + 2
    assert answer == 42
}

test fn answer_is_42() {
    let answer = 40 + 2
    assert answer == 42
}
```

Every source file declares its module. A module is a source namespace, while a
package is a versioned set of modules described by one manifest. Imports are
always explicit:

```loom
module hello

import utility.math.increment
```

A dependency alias in `loom.toml` grants access to a package; it does not create
an implicit import or rename the dependency's source modules.

## Targets

The manifest supports three target kinds:

| Kind | Purpose | Entry |
| --- | --- | --- |
| `bin` | Executable selected by `build` or `run` | Required for a non-default exported entry |
| `test` | Harness containing reachable `test fn` declarations | Not used |
| `lib` | Portable, validated `.loomlib` source package | Not used |

Select a named target with `--target`:

```sh
loomc check --target hello .
loomc build --target hello --output target/hello .
loomc test --target unit .
```

An exported executable entry must take no parameters and return `Unit`. The
`entry` value is a fully qualified module function such as `hello.main`.

A `.loomlib` is a versioned source-and-interface artifact for Loom package
dependencies. The consuming compiler checks and lowers its embedded sources
with the rest of the project; it is not a stable native ABI, shared library,
or FFI format.

## Dependencies and lockfiles

Path dependencies are a useful starting point:

```toml
[dependencies]
utility = { path = "../utility", version = "^1" }
```

Resolve the graph and write `loom.lock`:

```sh
loomc resolve .
loomc --locked check .
```

Commit `loom.lock` for executable projects and use `--locked` in automation so
an unexpected graph change fails instead of silently rewriting the lockfile.
See [Packages and dependencies](../guide/packages-and-dependencies.md) for path,
registry, artifact, feature, and offline behavior.

## Generated state

The default persistent cache lives below `target/loom/cache/v4`. Build outputs
also default below `target/loom`. These paths are implementation details and
should not be committed.

Inspect or prune the cache explicitly:

```sh
loomc cache stat .
loomc cache prune .
```

Use `--no-cache` for a cold compiler run or `--cache-dir DIR` to select another
cache root. Cache entries and generated artifacts are validated and versioned,
but they are not source-level compatibility guarantees.
